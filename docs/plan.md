# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 사용할 기술

`PRD.md` 10장에 정한 구성을 사용합니다.

| 구분 | 기술 | 역할 |
| --- | --- | --- |
| 화면 | React (Vite로 개발 환경 구성) | 사용자가 보고 누르는 화면. 서버에 요청을 보내고 결과를 보여줌 |
| 서버 | Python, FastAPI | 입력값 검사, 로그인 확인, 권한 확인, 데이터 저장과 조회 |
| 데이터베이스 연결 | SQLAlchemy, Alembic | SQLAlchemy는 SQLite와 PostgreSQL을 같은 코드로 다루게 해줌. Alembic은 데이터베이스 구조 변경(마이그레이션)을 기록함 |
| 데이터베이스 (개발·테스트) | SQLite | 내 컴퓨터에서 바로 개발하고 테스트 |
| 데이터베이스 (실제 서비스) | Supabase (PostgreSQL) | 인터넷에서 쓰는 실제 데이터베이스. 데이터베이스로만 사용 |

화면과 서버가 주고받는 흐름은 다음과 같습니다.

```text
사용자 ─ 브라우저(React 화면) ─ 요청 → FastAPI 서버 ─ 저장·조회 → SQLite(개발) / Supabase(실제)
                             ← 결과 ─              ← 결과 ─
```

## 3. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- **화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다.** React 화면은 누구나 조작할 수 있으므로, 모든 권한과 입력 조건은 FastAPI 서버에서 다시 검사합니다.
- 입력 조건(글자 수, 공백 처리 등)은 서버에서 최종 판단합니다. 화면에서도 같은 조건을 미리 안내할 수 있지만, 서버 검사를 대신하지 않습니다.
- 비밀번호는 원문을 저장하지 않고 안전한 방식(Argon2)으로 바꿔 저장합니다.
- 로그인 상태는 **화면의 JavaScript가 읽을 수 없는 쿠키(HttpOnly 쿠키)**에 담습니다. 화면에 들어간 악성 코드가 로그인 정보를 훔쳐가지 못하게 하기 위해서입니다.
- SQLite와 Supabase(PostgreSQL)에서 **같은 코드가 동작**하도록 한쪽 데이터베이스에만 있는 기능은 쓰지 않습니다.
- 데이터베이스 구조는 Alembic 마이그레이션으로만 바꿉니다. 데이터베이스 파일을 지우고 다시 만드는 방식으로 해결하지 않습니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, `node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- 꼭 필요한 패키지만 추가합니다. 새 패키지가 필요하면 이유와 함께 먼저 알립니다.

## 4. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ .venv/              # Python 가상환경, Git 제외
│  ├─ .env                # 서버 비밀 설정값, Git 제외
│  ├─ .env.example        # 설정 항목 이름만 기록
│  ├─ requirements.txt    # 서버 실행에 필요한 패키지와 정확한 버전
│  ├─ requirements-dev.txt# 테스트에만 필요한 패키지
│  ├─ alembic.ini
│  ├─ alembic/            # 데이터베이스 구조 변경 기록
│  ├─ app/
│  │  ├─ main.py          # FastAPI 시작점
│  │  ├─ core/            # 설정, 데이터베이스 연결, 비밀번호·로그인 처리
│  │  ├─ models/          # 데이터베이스 표 구조
│  │  ├─ schemas/         # 요청·응답 입력값 규칙
│  │  ├─ routers/         # 기능별 요청 주소 (회원, 기록, 공개, 댓글, 좋아요, 신고, 운영자)
│  │  └─ services/        # 권한 검사 등 여러 기능이 함께 쓰는 처리
│  ├─ scripts/            # 운영자 지정 등 관리용 명령
│  └─ tests/              # 서버 자동 테스트
├─ frontend/
│  ├─ package.json
│  ├─ vite.config.ts      # 개발 중 /api 요청을 서버로 전달
│  ├─ index.html
│  └─ src/
│     ├─ main.tsx
│     ├─ App.tsx          # 화면 주소(라우터) 연결
│     ├─ api/             # 서버 요청 함수
│     ├─ pages/           # 화면 단위 (회원, 홈, 공부 기록, 할 일, 오류 기록, 공개 기록, 운영자)
│     ├─ components/      # 메뉴, 카드, 입력칸, 확인창 등 공통 조각
│     └─ styles/          # 공통 CSS
├─ database/
│  └─ buildlog.sqlite3    # 개발용 데이터 파일, Git 제외
└─ docs/                  # 요구사항, 동작 설명서, 개발 문서
```

### 환경 변수 (`backend/.env`)

| 이름 | 의미 | 개발 값 예시 |
| --- | --- | --- |
| `DATABASE_URL` | 연결할 데이터베이스 주소 | SQLite: `database/buildlog.sqlite3` 파일 / 실제: Supabase 연결 주소 |
| `SECRET_KEY` | 로그인 쿠키를 위조하지 못하게 서명하는 비밀값 | 무작위로 생성 |
| `ENVIRONMENT` | 개발(`development`)인지 실제 서비스(`production`)인지 | `development` |

- 자동 테스트는 개발용 데이터 파일을 건드리지 않도록 테스트마다 별도의 임시 SQLite를 씁니다.

### 개발 중 실행 주소

| 대상 | 주소 |
| --- | --- |
| React 화면 | `http://localhost:5173` |
| FastAPI 서버 | `http://127.0.0.1:8000` |
| 서버 요청 주소 문서 | `http://127.0.0.1:8000/docs` (FastAPI가 자동으로 만들어줌) |

- 개발 중에는 React 개발 서버가 `/api`로 시작하는 요청을 FastAPI로 전달합니다. 그래서 브라우저 입장에서는 같은 주소로 보여 쿠키 로그인이 간단해집니다.

## 5. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가기 위한 핵심 조건 |
| --- | --- | --- |
| 0 | 개발 기준과 환경 확인 | 문서와 개발 환경에 충돌이 없음 |
| 1 | 실행 가능한 FastAPI 서버 뼈대 | 서버가 실행되고 상태 확인 요청에 응답함 |
| 2 | 실행 가능한 React 화면 뼈대 | 화면이 실행되고 서버 상태를 받아 보여줌 |
| 3 | 사용자 데이터 구조와 첫 데이터베이스 | 첫 마이그레이션과 사용자 모델 테스트 통과 |
| 4 | 회원가입·로그인·닉네임 | 회원 기능과 접근 제한 테스트 통과 |
| 5 | 세 가지 기록의 데이터 구조 | 저장·재실행·제약 조건 테스트 통과 |
| 6 | 공부 기록 전체 흐름 | 공부 기록 기능만 단독으로 완성 |
| 7 | 할 일 전체 흐름 | 할 일 기능만 단독으로 완성 |
| 8 | 오류 기록 전체 흐름 | 오류 기록 기능만 단독으로 완성 |
| 9 | 공개 기록·공개 범위·공개 검색 | 비공개 유출 없이 공개 기능 동작 |
| 10 | 댓글 | 댓글 조건과 권한 테스트 통과 |
| 11 | 좋아요 | 중복 방지와 취소 테스트 통과 |
| 12 | 신고와 운영자 확인 | 신고 저장·중복 방지·운영자 권한 확인 |
| 13 | 반응형 화면과 공통 실패 처리 | 360px 이상 화면과 지정 브라우저 확인 |
| 14 | Supabase 연결 확인 | Supabase에서 마이그레이션과 전체 테스트 통과 |
| 15 | 전체 통합 확인과 실행 문서 | `spec.md`의 완료 조건 전체 통과 |

- 각 기능 Phase(4, 6~12)는 **서버 → 화면** 순서로 만듭니다. 서버 요청을 먼저 만들고 자동 테스트로 확인한 뒤, 그 요청을 쓰는 React 화면을 만듭니다.

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 문서끼리 비교해 정해지지 않은 내용을 정리하고 결정을 요청합니다. ([7. Phase 0에서 결정한 항목](#7-phase-0에서-결정한-항목) 참고)
4. 사용할 Python, FastAPI, SQLAlchemy, Alembic, React, Vite의 서로 호환되는 안정 버전을 확인합니다.
5. Python과 Node.js가 설치되어 있고 버전이 맞는지 확인합니다.
6. SQLite가 Python 환경에서 사용 가능한지 확인합니다.
7. 개발 서버 주소, 데이터베이스 파일 위치, 환경 변수 이름을 확정합니다.
8. 테스트 명령과 서버 실행 명령을 `docs/setup.md`에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python, Node.js 실행 여부와 버전을 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인이 필요한 항목이 모두 결정되어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

### Phase 1. FastAPI 서버 뼈대 만들기

#### 목표

기능 없이도 FastAPI 서버가 실행되고, 상태 확인 요청에 응답하게 합니다.

#### 작업

1. `backend/.venv`에 가상환경을 만듭니다.
2. FastAPI, 실행 도구(Uvicorn), SQLAlchemy, Alembic, 설정 도구를 설치하고 정확한 버전을 `backend/requirements.txt`에 기록합니다.
3. 테스트 도구(pytest, httpx)를 설치하고 `backend/requirements-dev.txt`에 기록합니다.
4. `backend/app/main.py`에 FastAPI 시작점을 만듭니다.
5. 설정값을 `backend/.env`에서 읽도록 하고, `backend/.env.example`에는 항목 이름만 기록합니다. `SECRET_KEY`는 무작위로 생성해 `.env`에만 넣습니다.
6. `DATABASE_URL`에 따라 SQLite 또는 PostgreSQL에 연결하는 데이터베이스 연결 코드를 만듭니다. 개발 값은 `database/buildlog.sqlite3`입니다.
7. Alembic을 준비합니다. 이 Phase에서는 아직 표를 만들지 않습니다.
8. 상태 확인 요청(`GET /api/health`) 하나만 만듭니다.
9. 테스트가 임시 SQLite를 쓰도록 테스트 기본 설정을 만듭니다.
10. `.gitignore`에 SQLite 파일(`*.sqlite3`)과 테스트 생성 파일을 보완합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/requirements-dev.txt`
- `backend/.env.example`
- `backend/.env` (Git 제외)
- `backend/app/main.py`
- `backend/app/core/config.py`
- `backend/app/core/database.py`
- `backend/alembic.ini`
- `backend/alembic/`
- `backend/tests/conftest.py`
- `backend/tests/test_health.py`
- `.gitignore`

#### 확인 방법

- 서버가 오류 없이 시작되는지 확인합니다.
- `http://127.0.0.1:8000/api/health`에서 정상 응답이 오는지 확인합니다.
- `http://127.0.0.1:8000/docs`에서 요청 주소 문서가 보이는지 확인합니다.
- 상태 확인 자동 테스트가 통과하는지 확인합니다.
- `.env`와 SQLite 파일이 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 서버와 상태 확인 요청이 정상 동작해야 합니다.
- 아직 데이터베이스 표를 만들지 않습니다.

### Phase 2. React 화면 뼈대 만들기

#### 목표

React 화면이 실행되고, 서버에 요청을 보내 결과를 받아 보여줄 수 있게 합니다.

#### 작업

1. `frontend`에 Vite로 React 프로젝트를 만듭니다.
2. 화면 주소를 나누는 라우터(React Router)를 설치합니다.
3. 개발 중 `/api` 요청을 FastAPI 서버(`127.0.0.1:8000`)로 전달하도록 설정합니다.
4. 서버 요청 공통 함수를 만듭니다. 쿠키를 함께 보내고, 실패하면 이유를 돌려주게 합니다.
5. 모든 화면이 함께 쓰는 기본 틀(메뉴 자리, 본문 자리)과 밝은 배경의 기본 CSS를 만듭니다.
6. 서버 상태 확인 결과를 보여주는 임시 화면 하나를 만듭니다.
7. 화면 테스트 도구(Vitest, React Testing Library)를 준비합니다.

#### 예상 변경 파일

- `frontend/package.json`
- `frontend/package-lock.json`
- `frontend/vite.config.ts`
- `frontend/index.html`
- `frontend/src/main.tsx`
- `frontend/src/App.tsx`
- `frontend/src/api/client.ts`
- `frontend/src/components/Layout.tsx`
- `frontend/src/styles/base.css`
- `frontend/src/pages/HealthPage.tsx` (임시)
- `frontend/src/**/*.test.tsx`

#### 확인 방법

- 서버와 화면을 함께 켜고 `http://localhost:5173`을 열면 서버 상태가 보이는지 확인합니다.
- 서버를 끈 상태에서 열면 실패 안내가 보이는지 확인합니다.
- 화면 자동 테스트가 통과하는지 확인합니다.
- `node_modules`와 빌드 결과(`dist`)가 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 화면과 서버가 연결되어 동작해야 합니다.

### Phase 3. 사용자 데이터 구조와 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. 사용자 모델을 만듭니다.
   - 이메일: 필수, 중복 불가
   - 닉네임: 필수, 중복 불가, 2~20자, 한글·영문·숫자·밑줄만
   - 닉네임 비교용 값: 닉네임을 소문자로 바꾼 값. 이 값에 중복 불가 제약을 둠
   - 비밀번호: 원문 대신 Argon2로 바꾼 값만 저장
   - 운영자 여부: 기본값은 일반 사용자 (Phase 12에서 사용)
   - 가입 날짜·시간
2. 이메일은 저장 전에 소문자로 맞춰 대소문자만 다른 이메일이 중복 저장되지 않게 합니다. 닉네임은 입력한 모양 그대로 저장하고, 비교용 값으로 중복을 막습니다.
3. 비밀번호를 바꿔 저장하고 확인하는 기능을 만듭니다.
4. Alembic으로 첫 마이그레이션을 만들고 개발용 SQLite에 적용합니다.
5. 사용자 모델 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/models/user.py`
- `backend/app/core/security.py`
- `backend/alembic/versions/`
- `backend/tests/test_user_model.py`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 데이터베이스 단계에서 확인합니다.
- 대소문자만 다른 이메일(`Test@Mail.com`, `test@mail.com`)과 닉네임(`Coder`, `coder`)도 중복으로 막히는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.

#### 완료 조건

- 첫 마이그레이션과 사용자 모델 테스트가 모두 통과해야 합니다.
- 마이그레이션을 처음부터 다시 적용해도 같은 구조가 만들어져야 합니다.

### Phase 4. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업 — 서버

1. 회원가입 요청을 만듭니다.
   - 이메일과 닉네임의 앞뒤 공백 제거, 비밀번호는 입력한 그대로 검사
   - 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건 검사
   - 실패하면 어떤 칸이 왜 틀렸는지 돌려줌
2. 로그인 요청을 만듭니다.
   - 이메일은 대소문자를 구분하지 않고 확인
   - 이메일과 비밀번호가 맞으면 서명된 로그인 쿠키(HttpOnly)를 발급. 유효 기간 7일
   - 틀리면 "로그인 정보가 맞지 않다"는 하나의 안내만 돌려줌
3. 로그아웃 요청을 만듭니다. 로그인 쿠키를 지웁니다.
4. 현재 로그인한 사용자 정보를 돌려주는 요청을 만듭니다.
5. 로그인하지 않은 요청을 막는 공통 검사를 만듭니다. 이후 모든 기록 요청에 씁니다.
6. 닉네임 변경 요청을 만듭니다. 로그인한 본인 닉네임만 바꿀 수 있습니다. 내 닉네임의 대소문자만 바꾸는 것은 허용합니다.
7. 다른 사이트에서 몰래 요청을 보내는 공격(CSRF)을 막도록 쿠키와 요청 방식을 설정합니다.
8. 서버 자동 테스트를 작성합니다.

#### 작업 — 화면

9. 회원가입 화면: 실패하면 이유를 보여주고 이메일·닉네임은 유지, 비밀번호만 지움. 성공하면 로그인 화면으로 이동
10. 로그인 화면: 실패하면 이메일은 유지, 비밀번호만 지움. 성공하면 내 기록 홈으로 이동
11. 로그인하지 않은 사용자가 기록 화면 주소로 들어오면 로그인 화면으로 보냄
12. 내 기록 홈 화면의 뼈대: 공부 기록, 할 일, 오류 기록, 공개 기록, 계정 설정, 로그아웃 메뉴. 카드는 Phase 13에서 채움
13. 로그아웃 버튼: 누르면 로그인 화면으로 이동. 서버에 연결할 수 없어도 화면의 로그인 상태는 끝냄
14. 계정 설정 화면(닉네임 변경): 실패하면 이유를 보여주고 입력한 새 닉네임 유지

- 회원가입 성공 후 로그인 화면으로, 로그인 성공 후 내 기록 홈으로 이동하는지 확인합니다.

### Phase 5. 공부 기록·할 일·오류 기록의 데이터 구조

#### 목표

화면 작업 전에 세 가지 기록이 안전하게 저장될 공통 기반을 만듭니다.

#### 작업

1. 공부 기록 모델: 작성자, 제목, 내용, 공개 여부, 작성·수정 날짜·시간
2. 할 일 모델: 작성자, 제목, 완료 여부, 공개 여부, 작성·수정·완료 날짜·시간
3. 오류 기록 모델: 작성자, 오류 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부, 작성·수정·해결 날짜·시간
4. 새 기록은 기본 비공개, 새 할 일은 미완료, 새 오류는 미해결로 설정합니다.
5. 제목과 내용의 최대 길이를 데이터베이스와 입력 규칙 양쪽에 둡니다.
6. "해결 상태이면 해결 방법이 있어야 한다"는 규칙을 데이터베이스 단계에서도 검사합니다.
7. 날짜·시간은 모두 한국 시간으로 보여줄 수 있도록 기준 시간(UTC)으로 저장합니다.
8. 공통 입력 처리를 만듭니다: 앞뒤 공백 제거, 중간 띄어쓰기 유지, 공백만 있으면 빈 입력
9. 공통 권한 검사를 만듭니다: 작성자만 수정·삭제, 비공개는 작성자만 조회
10. 공통 목록 처리를 만듭니다: 한 페이지 20개, 없는 페이지 번호는 마지막 페이지로
11. 공통 검색 처리를 만듭니다: 검색어가 들어 있는 기록을 영문 대소문자 구분 없이 찾음. SQLite와 PostgreSQL에서 같은 결과가 나오게 함
12. 마이그레이션을 만들고 적용합니다.
13. 데이터 모델과 상태 전환 단위 테스트를 작성합니다.

- 기본 공개 상태와 기본 완료·해결 상태가 맞는지 확인합니다.

- 오류를 미해결로 되돌려도 해결 방법은 유지되는지 확인합니다.
- 서버를 종료하고 다시 실행해도 데이터가 남아 있는지 확인합니다.

6. 오류 제목과 오류 내용으로 내 오류 기록을 검색합니다. 영문 대소문자는 구분하지 않고, 필터를 고른 상태이면 그 안에서만 찾습니다.

8. 작성자만 해결 상태를 바꾸고 수정·삭제할 수 있게 합니다.

#### 작업 — 화면

9. 목록(필터·검색 포함), 만들기, 상세, 수정 화면을 만듭니다.
10. 저장·수정 성공 후 오류 기록 목록으로 이동합니다.
11. 상세 화면에 수정 날짜·시간을 보여줍니다.
12. 실패 시 이유를 보여주고 입력값을 유지합니다.

### Phase 9. 공개 범위·공개 기록·공개 검색

#### 목표

#### 작업 — 서버

1. 세 종류의 기록에서 작성자만 공개 여부를 바꾸게 합니다.
2. 공개 기록 목록 요청: **다른 사용자의** 공개 공부 기록, 할 일, 오류 기록을 합쳐 최신순으로, 20개씩 돌려줍니다. 요청한 사람 자신의 기록은 넣지 않습니다.
3. 기록 종류별 필터를 만듭니다.
4. 공개 검색: 공부 기록은 제목·내용, 할 일은 제목, 오류 기록은 오류 제목·내용·해결 방법에서 찾습니다. 영문 대소문자는 구분하지 않고, 종류를 고른 상태이면 그 안에서만 찾습니다. 빈 검색어이면 전체 공개 목록입니다.
5. 공개 기록에 작성자의 **현재** 닉네임을 함께 돌려줍니다.
6. 로그인하지 않은 요청은 거부합니다.
7. 비공개 기록이 주소 직접 입력이나 검색 결과로 노출되지 않게 합니다.
8. 영어 대소문자를 구분하지 않는 검색이 SQLite와 PostgreSQL에서 똑같이 동작하게 합니다.

#### 작업 — 화면

10. 공개 공부 기록·오류 기록 상세 화면을 만듭니다. 다른 사용자에게는 수정·삭제 버튼이 보이지 않습니다.

### Phase 10. 댓글 기능

#### 목표

공개된 공부 기록과 오류 기록에서만 댓글을 사용하게 합니다.

#### 작업 — 서버

1. 댓글 모델을 만듭니다. 댓글은 공부 기록 또는 오류 기록 **둘 중 하나만** 가리키도록 데이터베이스 단계에서 제한합니다.

5. 기록 작성자는 자신의 기록에 달린 댓글을 삭제할 수 있게 합니다.
6. 공개 할 일에는 댓글 요청 주소를 만들지 않습니다.
7. 기록이 비공개가 되면 댓글 데이터는 유지하되 다른 사용자에게 돌려주지 않습니다. 다시 공개되면 기존 댓글을 다시 돌려줍니다.
8. 기록을 삭제하면 그 기록의 댓글도 함께 삭제합니다.

11. 삭제 전 확인창을 보여줍니다.
12. 실패 시 이유를 보여주고 작성·수정 중인 댓글을 유지합니다.

### Phase 12. 신고와 운영자 확인

#### 목표

로그인 사용자가 공개 기록이나 댓글을 신고하고, 운영자만 신고 내용을 확인하게 합니다.

#### 작업 — 서버

1. 신고 모델을 만듭니다. 신고 대상은 공개 공부 기록, 공개 할 일, 공개 오류 기록, 댓글 중 **하나만** 가리키도록 하고, 대상의 종류도 함께 저장합니다.
2. 신고 이유는 1~500자로 검사하고 앞뒤 공백을 제거합니다.
3. 한 사용자가 같은 대상을 한 번만 신고하게 데이터베이스 제약을 둡니다.
4. 자기 기록과 자기 댓글에 대한 신고는 거부합니다.
5. 신고만으로 대상 기록이나 댓글을 자동 삭제하지 않습니다.
6. 대상 기록이나 댓글이 삭제되어도 신고는 남깁니다. 이때 대상 연결만 비우고, 운영자 목록에서 "대상이 삭제됨"으로 보여줍니다.

9. 대상 기록이 비공개가 되어도 신고 기록은 운영자가 확인할 수 있게 유지합니다.
10. 별도의 신고 처리 상태 기능은 만들지 않습니다.
11. 마이그레이션을 만들고 적용합니다.

13. 신고 성공과 실패 안내를 보여주고, 실패 시 신고 이유를 유지합니다.
14. 운영자에게만 보이는 신고 목록 화면(읽기 전용, 페이지 이동 포함)을 만듭니다.

### Phase 14. Supabase 연결 확인

#### 목표

개발·테스트에 쓰던 SQLite 대신 Supabase(PostgreSQL)에 연결해도 모든 기능이 똑같이 동작하는지 확인합니다.

#### 작업

1. Supabase 프로젝트의 데이터베이스 연결 주소를 `backend/.env`의 `DATABASE_URL`에 넣습니다. (사용자가 직접 넣음. 연결 주소에는 비밀번호가 들어 있으므로 문서나 코드에 적지 않음)
2. PostgreSQL 연결에 필요한 패키지를 추가하고 `requirements.txt`에 기록합니다.
3. Alembic 마이그레이션을 Supabase에 처음부터 적용합니다.
4. 전체 서버 자동 테스트를 Supabase용 **테스트 전용** 데이터베이스(또는 테스트 전용 영역)에서 실행합니다. 실제 데이터와 섞이지 않게 합니다.
5. SQLite와 결과가 다른 부분(대소문자 검색, 날짜·시간, 중복 제약 오류 등)이 있으면 고칩니다.
6. Supabase의 자동 공개 기능(Data API)으로 표가 인터넷에 직접 노출되지 않도록 설정을 확인합니다. BuildLog는 FastAPI 서버를 통해서만 데이터베이스에 접근합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/.env` (Git 제외)
- `backend/.env.example`
- `backend/app/core/database.py`
- 필요한 범위의 기존 코드와 테스트

#### 확인 방법

- Supabase에 마이그레이션이 오류 없이 적용되는지 확인합니다.
- 전체 서버 자동 테스트가 Supabase에서도 통과하는지 확인합니다.
- 화면에서 가입, 기록 작성, 공개, 댓글, 좋아요, 신고를 한 번씩 해보고 Supabase에 저장되는지 확인합니다.
- Supabase의 Data API로 BuildLog 표를 직접 읽을 수 없는지 확인합니다.

#### 완료 조건

- SQLite와 Supabase 양쪽에서 전체 자동 테스트가 통과해야 합니다.
- 비밀 연결 주소가 Git 기록 대상에 들어가지 않아야 합니다.
